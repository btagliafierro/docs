    The DualSPHysics Workflow¶

    Every DualSPHysics simulation goes through the same three stages:

    1. Pre-processing. GenCase reads your case definition (an XML file) and creates the initial particles.
    2. Running the case. The DualSPHysics solver advances the particles in time and writes the results.
    3. Post-processing. A set of small tools turn those results into files you can visualise (in ParaView) or plot (in Python, Excel, MATLAB, …).

    The three stages are separate programs that communicate only through files. A batch file in each case folder runs them in the right order, so a simulation normally starts with a single command. This page follows the 01_DamBreak example through all three stages.

    About the file names

    CaseName stands for the name of your case, e.g. CaseDambreak. The .bi4 files are DualSPHysics' own binary format: compact and fast to write, but not readable by other programs. That is why the post-processing stage exists.

    Pre-processing: defining the case with GenCase¶

    GenCase builds the initial state of the simulation from a definition file, CaseName_Def.xml. This file contains everything about the case:

    • the geometry: tanks, walls, obstacles, wavemakers, floating objects;
    • the fluid: where it is initially and with which properties;
    • the motion of moving objects, e.g. a piston wavemaker;
    • the simulation parameters: particle spacing, physical constants, formulation options, simulated time.

    GenCase is very fast: it creates millions of particles in seconds on an ordinary CPU.

    How particles are created¶

    GenCase places all particles on a regular Cartesian lattice. The spacing between lattice nodes is the particle spacing dp, the single most important parameter of a simulation: halving dp doubles the resolution, but multiplies the number of particles by 4 in 2-D and by 8 in 3-D.

    Objects are drawn onto the lattice. For each object, GenCase selects the lattice nodes that fall inside it, or on its surface, and creates particles only there. The diagram below shows this for a triangle in 2-D: the lattice is laid over the triangle's bounding box, the triangle's edges are traced, and particles are created at the nodes inside.

    Step 1 Geometry Definition
    1. Geometry Definition
    The user inputs the boundary geometric definition (XML surface description, STL mesh, or PLY CAD model) establishing the continuous shape volume.
    2. Lattice Creation
    GenCase overlays a uniform background 2D/3D grid (lattice) of candidate points spaced at inter-particle distance dp across the domain.
    3. Point-in-Polygon Testing
    A ray-casting / point-in-polyhedron algorithm evaluates each candidate point to test whether its coordinates lie strictly inside the defined shape.
    4. Particle Selection & Pruning
    All points outside the boundary are discarded. The surviving internal points are assigned SPH properties and exported as initial simulation particles.

    Because the geometry is described independently of the lattice, the same case can be run at any resolution just by changing dp. Nothing else in the definition file needs to change.

    Drawing geometry¶

    The definition file offers a set of drawing commands:

    Kind Commands
    Points and lines <drawpoint />, <drawpoints />, <drawline />, <drawlines />
    Surfaces <drawtriangle />, <drawquadri />, <drawtrianglesstrip />, <drawtrianglesfan />, <drawpolygon>, <drawtriangles />
    Volumes <drawpyramid />, <drawprism />, <drawbox />, <drawbeach />, <drawsphere />, <drawellipsoid />, <drawcylinder />, <drawwave />
    Imported geometry <drawfilestl />, <drawfileply />, <drawfilevtk />
    Transformations <move />, <scale />, <rotate />, <rotateline />
    Filling with fluid <fillpoint />, <fillbox />, <fillfigure />, <fillprism />

    For complex, real-world geometry, draw the object in any CAD tool, export it as STL, PLY or VTK, and load it with the matching <drawfile... /> command. Imported and drawn objects can be combined freely in the same case.

    The draw mode decides which lattice nodes of an object receive particles:

    • <setdrawmode mode="face" />: only the surface of the object;
    • <setdrawmode mode="solid" />: only the inside;
    • <setdrawmode mode="full" />: both.

    Once the walls exist, the fill commands flood a region with fluid up to those walls, which works even for very complex containers.

    Particle types and the mk number¶

    Each particle created is of one of three types, set before drawing:

    • fluid: <setmkfluid mk="..." />
    • boundary: <setmkbound mk="..." />
    • none (the nodes are left empty): <setmkvoid />

    The mk value is a marker that labels a group of particles sharing the same role, for example "the tank walls" or "the moving gate". Later you use it to give that group a motion, to make it a floating body, or to compute the force acting on it.

    The marker you write in the XML is not the final mk stored with the particles. GenCase shifts the numbers so that fluid and boundary markers never overlap:

    • mk of fluid particles = mkfluid + 1
    • mk of boundary particles = mkbound + 1 + fluidcount (usually fluidcount = 9)
    Source Container: mkfluid & mkbound Arrays
    Void
    ...
    mk=0
    mk=1
    mk=2
    mk=3..8
    mk=9
    mk=10
    mk=11
    mk=12
    Target Container: mk Array (fluidcount = 9)
    mkfluid=0 Fluid 0
    mkfluid=1 Fluid 1
    mkbound=0 Bound 0
    mkbound=1 Bound 1
    mkbound=2 Bound 2

    Check the final mk values

    GenCase writes the final mk of every particle group to CaseName.out. When a post-processing command needs an mk (for example -onlymk: in ComputeForces), take the value from that file.

    Fluid particles can also receive initial conditions with <initials />, for example an initial velocity (<velocity />) or a solitary wave (<velwave />), and groups of boundary particles can be declared as floating bodies with <floatings />.

    Running GenCase¶

    GenCase takes the definition file (without the _Def.xml ending) and the output name:

    GenCase_win64.exe CaseDambreak_Def CaseDambreak_out/CaseDambreak -save:all

    ./GenCase_linux64 CaseDambreak_Def CaseDambreak_out/CaseDambreak -save:all

    -save:all asks GenCase to also write the geometry as VTK files. Inside CaseDambreak_out/ you then find:

    File What it is
    CaseDambreak.xml the full case configuration, as read by the solver
    CaseDambreak.bi4 the initial particles (binary)
    CaseDambreak.out GenCase's log: number of particles, final mk values, warnings
    CaseDambreak_All.vtk, _Bound.vtk, _Fluid.vtk the initial particles (all, boundary only, fluid only) for ParaView
    other .vtk files additional diagnostic geometry

    Look before you run

    Open CaseDambreak_Bound.vtk and CaseDambreak_Fluid.vtk in ParaView before starting a long simulation. A misplaced wall or a tank filled to the wrong level is much cheaper to spot here than after hours of computation.

    Running the case¶

    GenCase prepares the initial particles and case files; the DualSPHysics solver then runs the numerical simulation. CPU execution uses the host processor, while GPU execution uses a compatible NVIDIA GPU with CUDA. Executables are available for Windows and Linux. Windows examples typically use BAT scripts; Linux examples use shell scripts or equivalent commands. These scripts show the complete preparation, simulation and post-processing sequence.

    For executable selection, command-line options, hardware requirements and Multi-GPU execution, see CPU, GPU and Multi-GPU Execution.

    The solver¶

    The DualSPHysics executable reads the files written by GenCase and simulates the flow. It comes in two versions:

    Version Windows Linux
    GPU (NVIDIA, CUDA) DualSPHysics5.4_win64.exe DualSPHysics5.4_linux64
    CPU (multi-core, OpenMP) DualSPHysics5.4CPU_win64.exe DualSPHysics5.4CPU_linux64

    The version number in the name (5.4 here) changes between releases; check the bin/windows or bin/linux folder of your installation for the exact names. CPU and GPU availability does not establish identical numerical results or a fixed speedup. Check feature compatibility and assess numerical agreement and runtime for the intended case, software build and hardware.

    The solver takes the case name (as written by GenCase, without extension) and the output folder:

    DualSPHysics5.4_win64.exe -gpu CaseDambreak_out/CaseDambreak CaseDambreak_out

    ./DualSPHysics5.4_linux64 -gpu CaseDambreak_out/CaseDambreak CaseDambreak_out

    -gpu selects the graphics card; use -cpu to run on the processor instead. While it runs, the solver prints its progress in the terminal: the simulated time reached, the number of particles, and an estimate of the remaining run time.

    The results are written to CaseDambreak_out/:

    File What it is
    data/Part_0000.bi4, Part_0001.bi4, … the state of all particles at each output time (one file per saved instant)
    data/PartOut_000.obi4 particles that left the domain during the simulation
    Run.out the solver's log: configuration, progress, warnings, total run time
    Run.csv, RunPARTs.csv run statistics, per output step, in table form

    Command-line options

    Run the solver with -h to list every option it accepts. Many parameters of the XML file (for example the simulated time or the formulation options) can be overridden from the command line. This is handy for quick tests without editing the case.

    The batch files¶

    Typing these commands by hand every time would be tedious, and the post-processing steps add many more. Each example therefore comes with batch files that run the whole chain. Their names tell you the system (w…_win64 for Windows, x…_linux64 for Linux) and the processor they use:

    File System Runs on
    wCaseDambreak_win64_GPU.bat Windows GPU
    wCaseDambreak_win64_CPU.bat Windows CPU
    xCaseDambreak_linux64_GPU.sh Linux GPU
    xCaseDambreak_linux64_CPU.sh Linux CPU

    A batch file is a plain text file: open it in any text editor to read or change it. All DualSPHysics batch files follow the same structure, in five blocks. The excerpts below are from xCaseDambreak_linux64_GPU.sh; the Windows .bat files contain the same steps in Windows syntax (set name=... instead of export name=..., and %name% instead of ${name}).

    1. Case name and output folders¶

    export name=CaseDambreak
export dirout=${name}_out
export diroutdata=${dirout}/data

    name must match the definition file (CaseDambreak_Def.xml). All results go to CaseDambreak_out/, with the particle data in its data/ subfolder.

    2. Where the executables are¶

    export dirbin=../../../bin/linux
export gencase="${dirbin}/GenCase_linux64"
export dualsphysicsgpu="${dirbin}/DualSPHysics5.4_linux64"
export partvtk="${dirbin}/PartVTK_linux64"
export measuretool="${dirbin}/MeasureTool_linux64"
# ... one line for each post-processing tool

    dirbin points to the folder with the programs, relative to the case folder. If you copy a case to another location, this is the line to update.

    3. What to do if results already exist¶

    If CaseDambreak_out/ already exists, the batch file stops and asks:

    The folder "CaseDambreak_out" already exists. Choose an option.
  [1]- Delete it and continue.
  [2]- Execute post-processing.
  [3]- Abort and exit.

    Option 2 is worth remembering: it keeps the simulation results and only reruns the post-processing, for example after you have changed which variables PartVTK writes.

    4. Pre-processing and simulation¶

    ${gencase} ${name}_Def ${dirout}/${name} -save:all
if [ $? -ne 0 ] ; then fail; fi

${dualsphysicsgpu} -gpu ${dirout}/${name} ${dirout}
if [ $? -ne 0 ] ; then fail; fi

    These are exactly the two commands of the previous sections. The line after each one checks whether the program finished successfully, and stops the whole chain if it did not. That way a GenCase error is never followed by a meaningless simulation.

    5. Post-processing¶

    The rest of the file runs the post-processing tools, each writing to its own subfolder of CaseDambreak_out/ (particles/, measuretool/, forces/, surface/, flow/). These commands are explained in the next section.

    Adapting a batch file to your own case

    The easiest way to set up a new case is to copy an example folder and change:

    1. name, to match your _Def.xml file;
    2. dirbin, if the folder has moved relative to bin/;
    3. the post-processing commands: delete those you do not need and adjust the options of the others (particle types, mk values, measurement points).

    On clusters, the same commands go into the job submission script. See the notes on cluster machines in Run Your First Simulation.

    Post-processing¶

    The solver's output, data/Part_####.bi4, is complete but not directly usable. The post-processing tools read it and extract what you need.

    The tools¶

    Tool What it does Typical output
    PartVTK converts particles to VTK or CSV, with a choice of particles and variables particles/PartFluid_####.vtk
    PartVTKOut the same for particles that left the domain particles/PartFluidOut_####.vtk
    BoundaryVTK writes the geometry of moving and floating boundaries at each output time surface .vtk files
    MeasureTool interpolates velocity, pressure or free-surface elevation at chosen points (numerical gauges) .csv time series, .vtk points
    ComputeForces computes the force exerted by the fluid on a group of boundary particles .csv time series
    FloatingInfo reports the motion of floating bodies: position, velocity, rotation .csv time series
    IsoSurface builds the free surface as a surface mesh, and slices through it surface/Surface_####.vtk
    FlowTool counts particles and flow through user-defined boxes .csv, .vtk
    TracerParts follows the trajectories of selected particles .vtk lines

    Every tool prints the full list of its options when run with -h.

    Running a post-processing tool¶

    All tools share the same pattern: -dirdata says where the particle data are, and one or more -save... options say what to write. For example, the Dam Break batch file converts the fluid particles to VTK with:

    PartVTK_win64.exe -dirdata CaseDambreak_out/data -savevtk CaseDambreak_out/particles/PartFluid -onlytype:-all,+fluid

    ./PartVTK_linux64 -dirdata CaseDambreak_out/data -savevtk CaseDambreak_out/particles/PartFluid -onlytype:-all,+fluid
    Option Meaning
    -dirdata CaseDambreak_out/data read the particle data from this folder
    -savevtk .../PartFluid write VTK files named PartFluid_0000.vtk, PartFluid_0001.vtk, …
    -onlytype:-all,+fluid start from no particles (-all), then add the fluid ones (+fluid)

    The particle selection reads left to right: -all removes everything, then each + adds a group back. The available groups are all, bound, fixed, moving, floating and fluid. Particles can also be selected by marker (-onlymk:), by position (-onlypos:) or by velocity (-onlyvel:).

    Two more options are worth knowing from the start:

    • -vars: chooses the variables written with each particle, for example -vars:+idp,+vel,+rhop,+press for particle id, velocity, density and pressure. Fewer variables make smaller files.
    • -savecsv writes a table instead of VTK files, ready to open in Python or Excel.

    Visualising the results in ParaView¶

    ParaView is a free, open-source visualisation program that reads VTK files directly. The steps below show the Dam Break particles coloured by velocity.

    1. Load the particles. File → Open, go to CaseDambreak_out/particles/ and select PartFluid_..vtk. ParaView groups the numbered files into a single time series. Click Apply in the Properties panel.

    2. Colour by velocity. In the toolbar, change the colouring from Solid Color to Vel. Click Rescale to Data Range if the colours look washed out.

    3. Show the tank. Open CaseDambreak_out/CaseDambreak_Bound.vtk (written by GenCase) and click Apply. The walls give the flow its context. In the Properties panel, lower their Opacity so they do not hide the fluid.

    4. Play the simulation. Press Play in the toolbar at the top. The time shown in the toolbar is the simulated time.

    5. Save an image or a video. File → Save Screenshot saves the current view; File → Save Animation saves every time step as images or as a video.

    Large simulations

    3-D simulations can have millions of particles per file. For a first look, write only the variables you need with -vars:, or only some output times with the -first: and -last: options of PartVTK.
