    Add a floating object¶

    Add a fluid-driven rigid body to a compatible 3-D fluid case, using CaseFloating_Def.xml as the reference. The excerpts below are additions to a case definition, not a complete XML file.

    Starting example¶

    Use examples/main/11_Floating/CaseFloating_Def.xml from your v6 package. Its boundary particles with mkbound="50" form a freely moving rigid box; the piston has prescribed motion under marker 10 and the tank is fixed under marker 20. No Chrono or MoorDynPlus coupling is required. See the 11_Floating catalogue entry.

    Start with a working 3-D DBC fluid case using Symplectic integration. Its fluid-generation step must select fluid marker 0 and use fillbox with modefill set to void, as in the reference. Marker 50 must be unused and within the range allocated by its mkconfig. The reference allocates 230 boundary markers and 9 fluid markers; those allocations do not need replacing when they already accommodate the selected identifiers.

    The literal geometry below assumes room for a box from (10, 2, 3) to (12, 4, 5) m. In the reference, the tank is 16 × 6 m in plan, the initial water level is 4 m, particle spacing is 0.1 m, and generation bounds run from (-1, -1, -1) to (17, 7, 6) m. These are case-specific assumptions, not settings to insert into an arbitrary case. Check your geometry, water level, resolution and expected body excursion before using the excerpts; adapt body dimensions, position and mass consistently if your case differs.

    The reference file already contains this body. Use it to identify the additions to your existing case; do not paste a second copy into the reference itself.

    Required XML modifications¶

    1. Draw the body before filling the fluid¶

    Location: case/casedef/geometry/commands/mainlist, before the existing fluid-marker selection and fillbox.

    Action: add the following commands.

    <setdrawmode mode="full" />
<setmkbound mk="50" />
<drawbox>
    <boxfill>solid</boxfill>
    <point x="10" y="2" z="3" />
    <size x="2" y="2" z="2" />
</drawbox>

    This draws the source box as boundary particles under marker 50. Keep it separate from the tank and other bodies. The existing void fill must follow these commands so that it fills only unoccupied nodes. Check fluid exclusion around the body; other fluid-generation methods require a separate ordering check.

    2. Identify the floating body and set its mass¶

    Location: case/casedef, after the existing motion section in the reference and before the closing casedef tag.

    Action: add this block. If floatings already exists, insert only the floating child into it.

    <floatings>
    <floating mkbound="50">
        <massbody value="10000" />
    </floating>
</floatings>

    The matching mkbound="50" classifies the drawn particles as one floating rigid body. Its total mass is 10,000 kg in this example; it is not a default for other bodies or a guarantee of buoyant equilibrium. The source leaves the centre of gravity and inertia for GenCase to calculate. Inspect the generated values for your particle distribution rather than adding guessed properties.

    Keep the box out of prescribed motion/objreal definitions. In the reference, only marker 10 appears there; marker 20 remains fixed. Use the local boundary identifier mkbound consistently, rather than substituting a generated global mk value from post-processing.

    3. Check the rigid-body interaction setting¶

    Location: case/execution/parameters.

    Action: retain an existing matching entry. Otherwise, add or modify the single RigidAlgorithm entry to use the source SPH interaction treatment:

    <parameter key="RigidAlgorithm" value="SPH" comment="Rigid Algorithm: FREE:collision-free, SPH, DEM, CHR:Chrono collision (default=SPH)" />

    This adopts the reference's solid-interaction model. A case using another contact or coupling model needs a separate compatibility check before changing it. Do not copy the remaining parameter block: preserve the working case's physical and numerical settings. The reference uses FtPause=0.0; an intentional warm-up interval in another case delays floating-body motion.

    Check your configuration¶

    These checks are for your edited case:

    1. Confirm that marker 50 is available and matches both the geometry commands and the floating definition. It must not also be assigned prescribed motion.
    2. Regenerate the case with compatible v6 GenCase. Inspect the particles: the box must be complete, inside the generation bounds, clear of existing solids and free of overlapping fluid particles.
    3. Inspect the generated floating-body classification, total mass, centre of gravity and inertia. Confirm that the piston and tank retain their intended moving/fixed classifications.
    4. Check the DBC/Symplectic setup, the SPH rigid-body entry, any warm-up interval and sufficient solver-domain clearance for the expected motion. Mass, immersion and fluid density must describe the intended physical configuration.
    5. Run and inspect your case using the existing execution workflow. Correct source XML and regenerate the particle data if the geometry is wrong; editing generated execution XML does not rebuild the particles.

    Reference and further details¶

    • Source XML: examples/main/11_Floating/CaseFloating_Def.xml in the v6 package. The corresponding Windows script is wCaseFloating_win64_GPU.bat; it calls GenCase and the v6 GPU solver. Use your package's compatible tools and retain the existing workflow.

    • Floating bodies and material properties in the Main Configuration XML Guide.
    • Rigid-body interaction parameters.
    • Official examples and full-package information. The public repository contains only some examples; locate this source file in your v6 package rather than assuming a public GitHub copy is identical.
