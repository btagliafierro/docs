    Case Structure¶

    The XML input file is organized into two main sections:

    • <casedef>: Defines the physical setup including fluid properties, domain geometry, and initial particle configuration

    • <geometry>: Specifies numerical methods, time integration parameters, and output settings

    • <floatings>: Specifies numerical methods, time integration parameters, and output settings

    • <normals>: Specifies numerical methods, time integration parameters, and output settings

    • <motion>: Specifies numerical methods, time integration parameters, and output settings

    • <normals>: Specifies numerical methods, time integration parameters, and output settings

    • <execution>: Specifies numerical methods, time integration parameters, and output settings

    • <special>: Specifies numerical methods, time integration parameters, and output settings
    • <parameters>: Specifies numerical methods, time integration parameters, and output settings
    <constantsdef>                      
    <gravity x="0" y="0" z="-9.81" comment="Gravitational acceleration" units_comment="m/s^2" />
    <rhop0 value="1000" comment="Reference density of the fluid" units_comment="kg/m^3" />
    <rhopgradient value="2" comment="Initial density gradient 1:Rhop0, 2:Water column, 3:Max. water height (default=2)" />
    <hswl value="0" auto="true" comment="Maximum still water level to calculate speedofsound using coefsound" units_comment="metres (m)" />
    <gamma value="7" comment="Polytropic constant for water used in the state equation" />
    <speedsystem value="0" auto="true" comment="Maximum system speed (by default the dam-break propagation is used)" />
    <coefsound value="20" comment="Coefficient to multiply speedsystem" />
    <speedsound value="0" auto="true" comment="Speed of sound to use in the simulation (by default speedofsound=coefsound*speedsystem)" />
    <coefh value="1.0" comment="Coefficient to calculate the smoothing length (h=coefh*sqrt(3*dp^2) in 3D)" />      
    <_hdp value="2" comment="Alternative option to calculate the smoothing length (h=hdp*dp)" />
    <cflnumber value="0.2" comment="Coefficient to multiply dt" />          
</constantsdef>

    Constants Definition¶

    The <constantsdef> section establishes the fundamental physical properties and numerical coefficients that govern the simulation behavior.

    Fluid Properties¶

    <gravity x="0" y="0" z="-9.81" comment="Gravitational acceleration" units_comment="m/s^2" />
<rhop0 value="1000" comment="Reference density of the fluid" units_comment="kg/m^3" />
<gamma value="7" comment="Polytropic constant for water used in the state equation" />

    Gravity: Generally, it is used to simulate gravity's pull, and in this case it is set to -9.81 m/s² in the negative z-direction (Earth's gravitational acceleration) in SI. The \(x\) and \(y\) components are zero since gravity acts only vertically.

    Reference density (rhop0): The reference density of the fluid being simulated. This value is used in the equation of state to relate pressure and density. All density calculations reference this baseline value.

    Gamma: The polytropic constant (\(\gamma\)=7) used in the weakly compressible equation of state for water. This value provides a good balance between computational efficiency and physical accuracy for liquid flows.

    Density Initialization¶

    <rhopgradient value="2" comment="Initial density gradient 1:Rhop0, 2:Water column, 3:Max. water height (default=2)" />

    Density gradient mode: This parameter is used for the initialization of the density field for the fluid particles. Option 1 assigns \(\rho_0\) to all particles; Option 2 means the initial density distribution accounts for the hydrostatic pressure gradient in the water column, following the gravity direction, creating a physically realistic initial condition. This may help reduce initial transients when the simulation starts. Option 3 uses the max value of pressure according to the whole domain and the follows a global gradient rather than a local one. This option can be useful for floting body initialization.

    Speed of Sound Configuration¶

    <hswl value="0" auto="true" comment="Maximum still water level to calculate speedofsound using coefsound" units_comment="metres (m)" />
<speedsystem value="0" auto="true" comment="Maximum system speed (by default the dam-break propagation is used)" />
<coefsound value="20" comment="Coefficient to multiply speedsystem" />
<speedsound value="0" auto="true" comment="Speed of sound to use in the simulation (by default speedofsound=coefsound*speedsystem)" />

    Automatic speed of sound calculation: The speed of sound is automatically computed based on the maximum expected flow velocity. The auto="true" flag enables this automatic calculation.

    Speed system: Represents the characteristic velocity scale of the problem. For dam breaks, this is typically estimated from Torricelli's formula: \(v = \sqrt{2gh}\), where \(h\) is the initial water height, taken as max position minus the min position of fluid particles.

    Sound speed coefficient: The artificial speed of sound is usually set to 20 times the maximum system speed. This ensures that density fluctuations remain small (typically \(\leq\) 1%) while maintaining numerical stability. However, this definition may be case dependent. A higher coefficient makes the fluid less compressible but requires smaller time steps.

    Note

    Why artificial speed of sound?: Real water has a speed of sound around 1500 m/s, which would require mush smaller time steps. By using an artificially reduced speed of sound (typically 10-50 m/s for these flows), this approach allows maintaining weakly compressible behavior while making the simulation computationally feasible. However, this reduction applies only to scaled systems.

    Smoothing Length¶

    <coefh value="1.0" comment="Coefficient to calculate the smoothing length (h=coefh*sqrt(3*dp^2) in 3D)" />      
<_hdp value="2" comment="Alternative option to calculate the smoothing length (h=hdp*dp)" />

    Smoothing length coefficient: The smoothing length \(h\) determines the size of the interaction region between particles. With coefh=1.0, the smoothing length is calculated as \(h = \text{coefh}(1.0) × \sqrt{3dp^2}\) in 3D, which equals approximately \(1.73\cdot dp\).

    Alternative formula: The commented _hdp parameter shows an alternative approach where \(h = 2\cdot dp\). The underscore prefix disables this option, so in this case the coefh formula is used instead.

    Note

    The smoothing length defines the "reach" of each particle's influence. Particles within a distance of \(2h\) from each other can interact. Larger \(h\) values create smoother fields but may over-diffuse sharp features.

    Time Step Control¶

    <cflnumber value="0.2" comment="Coefficient to multiply dt" />

    CFL number: The Courant–Friedrichs–Lewy (CFL) number of 0.20 is used to determine the integration time step. The actual time step is computed as \(dt = 0.2 \cdot h/c\), where \(c\) is the speed of sound. Lower CFL values ensure stability but increase computational time. A value of 0.20 is conservative and appropriate for violent flows like dam breaks.

    Marker Configuration¶

        <mkconfig boundcount="230" fluidcount="9">
        <mkorientfluid mk="0" orient="Xyz" />
    </mkconfig>

    Boundary markers: Up to 240 different boundary types can be defined (mk=0 to mk=239). This allows for tracking different wall sections, obstacles, or boundary conditions separately.

    Fluid markers: Up to 9 different fluid types can be defined (mk=0 to mk=8). This is useful for multi-phase flows or tracking different fluid regions.

    Execution Parameters¶

    The <execution> section controls the numerical methods and simulation settings.

    Output Precision¶

    <parameter key="SavePosDouble" value="0" comment="Saves particle position using double precision (default=0)" />

    Single precision output: With value="0", particle positions are saved in single-precision (32-bit) format, reducing file sizes by ~50% compared to double precision. Internal calculations still use double precision for accuracy; this only affects output files.

    When to use double precision: Use value="1" for cases requiring very precise particle tracking over long times or when post-processing requires high precision (e.g., computing derivatives).

    Time Integration¶

    <parameter key="StepAlgorithm" value="1" comment="Step Algorithm 1:Verlet, 2:Symplectic (default=1)" />
<parameter key="VerletSteps" value="40" comment="Verlet only: Number of steps to apply Euler timestepping (default=40)" />

    Verlet algorithm: Option 1 uses the velocity-Verlet scheme, which is second-order accurate in time and preserves energy well. It's the standard choice for SPH simulations.

    Symplectic alternative: Option 2 is a symplectic integrator that may provide better long-term energy conservation but is rarely needed for short dam break simulations.

    Euler initialization: The first 40 time steps use a simpler first-order Euler method. This "warm-up" period allows the particle configuration to settle from the idealized initial condition before switching to the more accurate Verlet scheme. This reduces initial numerical oscillations.

    Kernel Function¶

    <parameter key="Kernel" value="1" comment="Interaction Kernel 1:Cubic Spline, 2:Wendland (default=2)" />

    Cubic Spline kernel: Option 1 uses the standard cubic spline (M4 cubic) kernel function. This kernel has compact support (particles interact only within distance 2h) and provides good balance between smoothness and computational efficiency.

    Wendland alternative: Option 2 provides a C² continuous kernel with better tensile stability properties but is slightly more computationally expensive.

    Physical role: The kernel function W(r,h) acts as a weighting function, determining how much influence nearby particles have on each other. The cubic spline has a peak at r=0 and smoothly decreases to zero at r=2h.

    Viscosity Model¶

    <parameter key="ViscoTreatment" value="1" comment="Viscosity formulation 1:Artificial, 2:Laminar+SPS, 3:Laminar (default=1)" />
<parameter key="Visco" value="0.1" comment="Viscosity value. Typically 0.01 for Artificial and 1e-6 m^2/s (water kinematic viscosity) for Laminar" />
<parameter key="ViscoBoundFactor" value="1" comment="Multiply viscosity value with boundary (default=1)" />

    Artificial viscosity: Option 1 uses an artificial viscosity term with dimensionless coefficient α=0.1. This approach: - Provides numerical stability by damping high-frequency oscillations - Prevents particle penetration through boundaries - Is computationally efficient - Does not directly represent physical viscosity (water's kinematic viscosity is 10⁻⁶ m²/s)

    Alternative formulations: - Option 2: Laminar viscosity plus Sub-Particle Scale (SPS) turbulence model for more physical representation - Option 3: Pure laminar viscosity for low-Reynolds flows

    Viscosity at boundaries: ViscoBoundFactor="1" means boundary particles use the same viscosity coefficient as fluid particles. Setting this >1 can help prevent fluid particles from penetrating solid walls in violent flows.

    Typical values: For artificial viscosity in dam breaks, α ranges from 0.01 (less dissipative) to 0.1 (more stable). The value 0.1 is conservative and appropriate for this violent flow case.

    Density Diffusion Term¶

    <parameter key="DensityDT" value="2" comment="Density Diffusion Term 0:None, 1:Molteni, 2:Fourtakas, 3:Fourtakas(full) (default=0)" />
<parameter key="DensityDTvalue" value="0.1" comment="DDT value (default=0.1)" />

    Fourtakas formulation: Option 2 implements the density diffusion term proposed by Fourtakas et al., which: - Reduces long-term density drift and accumulation errors - Smooths density fields without excessive dissipation - Improves pressure field quality, especially near boundaries - Is more computationally efficient than option 3 (full formulation)

    Diffusion coefficient: δ=0.1 controls the strength of density diffusion. Higher values provide more aggressive density correction but may over-smooth the solution.

    Why density diffusion is needed: SPH simulations can accumulate density errors over time due to particle disorder and boundary interactions. The density diffusion term acts as a corrective mechanism, nudging particle densities back toward their correct values.

    Alternative options: - Option 0: No density diffusion (may lead to density fluctuations) - Option 1: Molteni formulation (older approach) - Option 3: Full Fourtakas formulation (more accurate but slower)

    Particle Shifting¶

    <parameter key="Shifting" value="0" comment="Shifting mode 0:None, 1:Ignore bound, 2:Ignore fixed, 3:Full (default=0)" />
<parameter key="ShiftCoef" value="-2" comment="Coefficient for shifting computation (default=-2)" />
<parameter key="ShiftTFS" value="0" comment="Threshold to detect free surface. Typically 1.5 for 2D and 2.75 for 3D (default=0)" />

    No shifting: With value="0", particles maintain their Lagrangian positions without artificial displacement. This is appropriate for violent flows like dam breaks where natural particle disorder is physical.

    Shifting alternatives: - Options 1-3 activate particle shifting techniques that improve particle distribution and reduce void formation - Useful for low-Reynolds number flows or long-duration simulations - Can introduce non-physical effects in highly dynamic flows

    Shift coefficient: The value -2 would be used if shifting were activated. Negative values indicate the shifting direction opposes concentration gradients.

    Free surface detection: Would determine which particles are shifted if shifting were active. Not relevant here since shifting is disabled.

    Rigid Body Algorithm¶

    <parameter key="RigidAlgorithm" value="1" comment="Rigid Algorithm 0:collision-free, 1:SPH, 2:DEM, 3:Chrono (default=1)" />
<parameter key="FtPause" value="0.0" comment="Time to freeze the floatings at simulation start (warmup) (default=0)" units_comment="seconds" />

    SPH rigid body forces: Option 1 computes forces on rigid bodies (like the building) using standard SPH pressure and viscous force calculations. The building is treated as a fixed rigid body.

    Alternative methods: - Option 0: No interaction (particles pass through) - Option 2: Discrete Element Method for contact mechanics - Option 3: Chrono physics engine for complex multi-body dynamics

    No floating bodies: FtPause="0.0" is irrelevant here since the building is fixed, not floating. For floating objects, this parameter allows them to remain stationary during an initial warm-up period before dynamics begin.

    Time Step Calculation¶

    <parameter key="CoefDtMin" value="0.05" comment="Coefficient to calculate minimum time step dtmin=coefdtmin*h/speedsound (default=0.05)" />
<parameter key="DtIni" value="0" comment="Initial time step. Use 0 to default use (default=h/speedsound)" units_comment="seconds" />
<parameter key="DtMin" value="0" comment="Minimum time step. Use 0 to default use (default=coefdtmin*h/speedsound)" units_comment="seconds" />
<parameter key="DtFixed" value="0" comment="Fixed Dt value. Use 0 to disable (default=disabled)" units_comment="seconds" />
<parameter key="DtAllParticles" value="0" comment="Velocity of particles used to calculate DT. 1:All, 0:Only fluid/floating (default=0)" />

    Minimum time step coefficient: The minimum allowed time step is dt_min = 0.05 × h/c ≈ 0.05 × 0.0147m / 40m/s ≈ 1.8×10⁻⁵ s. This prevents the simulation from taking unreasonably small steps that would make it impractically slow.

    Automatic initial time step: DtIni="0" means the code automatically selects the initial time step based on dt = CFL × h/c.

    Automatic minimum time step: DtMin="0" uses the formula dt_min = 0.05 × h/c automatically.

    Variable time stepping: DtFixed="0" enables adaptive time stepping. The code automatically adjusts dt each step based on: - Maximum particle velocity - Speed of sound - CFL condition - Force magnitudes

    This is essential for dam breaks where velocities change dramatically over time.

    Time step based on fluid only: DtAllParticles="0" means the time step is determined by fluid particle velocities only, not boundary particles (which are stationary). This is appropriate since boundaries don't move.

    Typical time step evolution: In a dam break: - t=0: Small velocities → relatively large dt ≈ 10⁻⁴ s - t=0.1-0.5s: Peak velocities → minimum dt ≈ 10⁻⁵ s - t>1s: Flow slows → dt increases again

    Simulation Duration and Output¶

    <parameter key="TimeMax" value="1.6" comment="Time of simulation" units_comment="seconds" />
<parameter key="TimeOut" value="0.01" comment="Time out data" units_comment="seconds" />

    Output frequency: Data is saved every 0.01 seconds, producing 1.6/0.01 = 160 output files. This provides sufficient temporal resolution for accurate visualization and analysis without creating excessive file sizes.

    Particle Validity Checks¶

    <parameter key="PartsOutMax" value="1" comment="%/100 of fluid particles allowed to be excluded from domain (default=1)" units_comment="decimal" />
<parameter key="RhopOutMin" value="700" comment="Minimum rhop valid (default=700)" units_comment="kg/m^3" />
<parameter key="RhopOutMax" value="1300" comment="Maximum rhop valid (default=1300)" units_comment="kg/m^3" />

    Maximum particle loss: Up to 1% of fluid particles (value="1" means 100×1%=1% as a decimal fraction) can exit the domain or become invalid before the simulation terminates with an error. This tolerance accounts for spray particles and splashing.

    Density validity range: Particles with density outside 700-1300 kg/m³ are considered invalid and removed. This represents: - Lower limit: 70% of reference density (indicates excessive expansion/void) - Upper limit: 130% of reference density (indicates excessive compression)

    Why these limits?: In weakly compressible SPH, density variations should remain small (<10% ideally). The ±30% range provides tolerance for numerical oscillations while catching catastrophic errors like particle penetration or void formation.

    What happens to invalid particles: They are removed from the simulation and counted toward the PartsOutMax limit. If this limit is exceeded, the simulation terminates early, indicating numerical instability or poor parameter choices.

    Simulation Domain¶

    <simulationdomain comment="Defines domain of simulation">
    <posmin x="default" y="default" z="default" comment="e.g.: x=0.5, y=default-1, z=default-10%" />
    <posmax x="default" y="default" z="default + 50%" />
</simulationdomain>

    Automatic domain sizing: x="default", y="default", z="default" means the simulation domain is automatically determined from the initial minimum and maximum particle positions.

    Extended upper boundary: z="default + 50%" extends the upper boundary by 50% in the z-direction. If the initial maximum z-position, providing space for: - Water splashing above the building - Spray and droplet formation - Wave run-up on the building

    Why extend only the top?: Water cannot splash downward through the floor or sideways through the walls, but vertical splashing is expected and needs accommodation.

    Alternative specifications: You could manually set boundaries like x="0", y="0", z="-0.1" for posmin and x="2", y="1", z="1" for posmax to have full control over the computational domain.
